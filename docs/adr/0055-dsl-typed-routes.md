# ADR 0055 — Typed routes in `.vs`: native enums, generic native types and root inputs

- Status: Proposed
- Date: 2026-10-27

## Context

Rust apps route with `viso_ui::router`: a route enum, a `Navigator<R>` handle over the back
stack, a `RouterView` outlet and the `routes!` table. A `.vs` view has to drive the same
navigator (DSL U11): read `current()` and `can_pop()` reactively, `push`, `replace`, `pop`
and `reset` from handlers, place the outlet, and answer `back_requested`. Four things were
missing:

- A native enum was only a list of variant indices. `.vs` could name a variant but could not
  build one with fields or `match` on it, and a Rust enum with fields had no schema.
- The native schema had no generic types, so `Navigator<Route>` could not be typed.
- A view mounted from Rust could not take inputs: `view!` rejected a view that reads one.
- No `.vs` node placed a Rust-built outlet.

## Decision

- **A native enum is an enum its library declares.** The compiler gives the schema enum at
  `path` the symbol `native_enum(path)`, declares its variants as an ordinary enum's, and
  binds an import of it as a type. It is built, compared and exhaustively matched like a
  `.vs` enum, with the same value layout: a unit variant is its index, a payload variant the
  aggregate of its fields tagged with its index.
  - `NativeType::payloads` gives each variant's fields (`VariantFields`), by position or by
    name, and is carried in `natives.json`.
  - `#[derive(NativeData)]` on a Rust enum derives the schema and `NativeValue`. Variant
    names are the Rust names in snake case unless `#[native(name = "..")]` renames them.
- **Generic native types.** `NativeType::params` names a handle type's type parameters. In
  its methods, `SchemaTy::Param(i)` is the receiver's `i`-th type argument. The compiler
  types `Navigator<Route>` as `Ty::Native(id, [Route])` and substitutes the arguments into
  each method's signature. Values cross the boundary untyped, and the Rust side converts
  them with `NativeValue`.
- **`viso::nav`** is a standard library:
  - `Navigator<R>` has the methods `current() -> R`, `can_pop() -> Bool` and
    `depth() -> I64` (`fn`), and `push(R)`, `replace(R)`, `pop() -> Bool` and `reset(R)`
    (`action`).
  - Its handle holds a `RouteStack`, a trait the view implements over a Rust
    `RouterView<R>`.
  - A navigation edits the stack at once and marks it changed. When the call returns, the
    view's host raises the navigator's revision cell, so the transaction's navigations land
    together at the flush, as in Rust.
- **Root inputs from Rust.** `view!("shell.vs", nav: expr)` passes the root component's
  inputs.
  - Each value converts through `ViewInput`. A scalar fills a mirrored cell.
  - A `RouterView<R>` becomes the `Navigator<R>` input. Its slot is tracked through the
    navigator's own revision cell, so every binding and computed value that reads `nav`
    depends on the navigation, with no dynamic dependency.
  - An input the macro is not given, and that has no default, is a compile error naming it.
  - A Rust value of another type than the input's does not compile (a `const` assertion
    on the value's `ViewInput::TY`).
- **The app's own native libraries.** The route enum is the app's. Native package
  discovery takes the app's own package as well when its manifest declares
  `[package.metadata.viso.natives]`: its library target names the libraries `crate::NATIVES`,
  its other targets (the binary, the tests) through the library crate, and a package of
  binaries alone in each binary.
- **`RouterView` node.** It takes `navigator: Navigator<_>` and reports
  `back_requested(BackRequest)`.
  - It builds the navigator's Rust outlet inside itself, once, so pages come from the Rust
    `routes!` table and may be `view!`s (an arm's page may return anything).
  - A system back action fires `back_requested` first; `e.prevent_default()` keeps the page.

## Alternatives

- **Native enums as their own type kind (`Ty::Native`) with payloads.** That needs a
  second path for construction, patterns and exhaustiveness beside the `.vs` enum's. One
  enum model is smaller and gives `match` over `Key` for free.
- **A per-route navigator type generated by the derive (`RouteNavigator`).** That avoids
  generic natives but multiplies the schema and names a type the spec does not.
- **A hidden slot per navigator, refilled when its revision moves (the game-query
  link).** It needs a new package section and link kind. Aliasing the input's tracked cell
  to the navigator's revision gives the same dependency with what the view already has.
- **A DSL-held route stack.** Deep links and Rust pages need the Rust navigator, so two
  sources of truth would have to be kept in step.

## Consequences

- A persisted or snapshotted state of a native enum type hashes its type as an enum, so
  stored values from before the change load as mismatched once.
- A library-qualified path to a native variant (`game::Key::Space`) no longer resolves.
  The enum is imported and named instead.
- The DSL node's `back_requested` takes the place of the Rust outlet's own
  `on_back_requested`.
- A root input exists only for the `view!` mount. A view mounted from a release package, or
  re-mounted by the development runtime, still gets each input's default.
